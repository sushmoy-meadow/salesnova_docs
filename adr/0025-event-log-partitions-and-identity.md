# ADR-0025 — The event log's partitions are the application's, and its identity is tenant-first

**Status:** Accepted · **Date:** 2026-08 · **Deciders:** Engineering

## Context

The `event` table is range-partitioned by month from day one. That decision is already made and
argued elsewhere; what it forces are two smaller ones that had no obvious answer.

**Who creates next month's partition.** A month with no partition does not degrade gracefully — the
insert is refused outright, and an event that was refused cannot be reconstructed afterwards. The
usual answer is the `pg_partman` extension, which needs to be installed in the cluster.

**What the primary key is.** Postgres requires the partition column in every unique constraint on a
partitioned table, so the key cannot be `id` alone. But this project also requires that a
tenant-scoped table lead every composite index with `organization_id`, and that rule is enforced by
a test that walks the live schema. `(id, occurred_at)` satisfies Postgres and fails the rule.

## Decision

**Partitions are created by a scheduled application command, not by a database extension.**
`event:partitions` runs daily and builds the current month plus the configured runway, clamped to
three months as a floor.

**The migration builds the floor and nothing more.** A migration whose output depends on an
environment variable produces a different table on a fresh database than on an existing one; the
schema layer needs only enough runway to accept the first insert, and the tunable runway belongs to
the command that runs every day.

**The primary key is `(organization_id, id, occurred_at)`.**

## Consequences

- The runway is visible in the application: a partition that failed to appear is a failed scheduled
  command with a log line, not a silent gap in a cluster-side job table. It also means a managed
  Postgres that will not install extensions is not a blocker.
- Daily rather than monthly, deliberately: a monthly run that fails has no second attempt before the
  month it was meant to create arrives.
- The command is idempotent — it reads `pg_inherits` and creates only what is missing — so running
  it twice, or running it on two app servers, costs a query.
- The mechanism takes the table as a parameter rather than naming the event log, because two more
  tables are already specified to partition the same way. It deliberately does not attach an
  append-only guard to what it creates: a partitioned table is not necessarily an immutable one, so
  the caller that knows applies the guard to the names it gets back.
- Every access path that reaches an event knows its tenant, and the key serves them: a causal chain
  never crosses an organisation, so walking one by `causation_id` uses the key's leading pair. A
  lookup by bare `id` does not, and there is no index for one, because nothing in the product asks
  for an event without knowing whose it is.
- `id` is not unique on its own at the database level. It is a UUIDv7 and it is generated by the
  application, so this is a theoretical exposure rather than a practical one — but a writer that
  supplies its own id cannot rely on the database to reject a repeat.
- Retention is not implemented here. Detaching an old partition is instant where deleting tens of
  millions of rows is not, and the role that may detach one is not the role the application connects
  as — the same separation the audit trail uses.

## Alternatives

**`pg_partman`.** Fewer moving parts in the application and a well-tested implementation. Rejected
because it puts the guarantee in a place the application cannot see: the failure mode we care about
is "next month never got created", and we would rather that be a red scheduled command than a row in
an extension's config table nobody reads. Reconsider if partition maintenance grows past creation.

**`(id, occurred_at)` as the key, with the tenancy rule exempted for primary keys.** Rejected: the
rule is enforced precisely so that nobody has to remember it, and an exemption list is the beginning
of the rule not being enforced. The wider key costs bytes and answers both requirements honestly.

**Creating partitions lazily, on the first insert of a month.** Rejected: it puts DDL on a request
path, takes a lock the writers queue behind, and fails at exactly the moment the log is busiest.
