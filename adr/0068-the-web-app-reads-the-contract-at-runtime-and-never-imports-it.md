# ADR-0068 — The web app reads the contract at runtime, and never imports it

**Status:** Accepted · **Date:** 2026-08 · **Deciders:** Engineering

## Context

`TASK-ARCH-013` is the first slice whose two halves have to agree on a payload of any size. The API
assembles thirteen top-level fields for `GET /bootstrap`; the web app renders its navigation rail,
its badge counts and its warning banners from them and from nothing else. Both repos have a quality
gate, both were green throughout, and neither gate can see the other repo — so both would have
stayed green if the two halves had disagreed about a single field name.

The API already publishes a machine-readable answer. `salesnova_backend/contracts/openapi.json` and
its generated `contracts/api-types.ts` are regenerated by `npm run api:generate`, and
`api:check` fails the backend gate when the committed pair drifts from what the code produces. So
the contract exists, it is enforced, and it is typed. The obvious move is to import it.

It does not survive contact with how the two repos are built. They are independent checkouts with
independent CI; a clean clone of the web app has no sibling directory to reach into, so a relative
import across the two is a path that resolves on a developer's laptop and nowhere else. Vendoring a
copy into the web app replaces that with a second copy to keep honest, and the copy is stale exactly
when it matters — the day somebody changes the payload and does not run the sync.

The deeper objection is that a TypeScript type is not a check. It disappears at build. A field the
API renamed, a null the API started sending, a member whose organisation resolves to a payload
shaped differently: every one of those is a runtime fact, and an imported type has nothing to say
about any of them. It would have made the halves *look* joined while leaving the join untested.

## Decision

**The web app validates every response with its own Zod schema, hand-written against the published
contract. It imports nothing from the API's checkout.**

`src/lib/shell/bootstrap.ts` holds the schema for the shell payload, in the shape the seam already
uses for every other endpoint (`src/lib/auth/api-envelope.ts`, and the smaller schemas beside it).
Everything the shell renders is required, so a payload missing a field fails at the seam rather than
reaching a component that would render an empty navigation rail and look fine doing it.

Three things enforce the agreement, and none of them is a type:

- The API's own contract tests assert the published schema against the specification, field by
  field, in both directions.
- The web app's schema tests parse a payload transcribed from that published contract.
- A `fullstack` slice is closed on a demo run against both live servers, which is the only check
  that sees both halves at once.

## Consequences

The field list exists in two places and is kept in step by hand. That is the cost, and it is
deliberate: the alternative was a build-time coupling that could not be built in CI, or a vendored
copy that goes stale silently. A schema written by hand goes wrong loudly, on the first response.

A slice whose demo cannot be exercised does not close. That rule is what makes the arrangement safe;
without it the two gates would again be two green lights over an untested join.

Percentage-rollout flags stay out of the payload for the same reason the schema is strict: a value
decided per request cannot live in a response cached per organisation without the two disagreeing on
the next cache hit.
